# Dependencies

Researched: **2026-10-09** from the PyPI JSON API and the OSV advisory API.
Full comparison tables (including the Node and Go candidates) are in
[research/interface-and-stack.md](research/interface-and-stack.md).

Status: **accepted** with the stack decision in
[ARCHITECTURE.md](ARCHITECTURE.md) (D-2).

## Policy

- A dependency is added only when it replaces code we would otherwise have to
  get right and maintain ourselves (a web framework, a TLS-correct HTTP
  client, an AEAD implementation). Not to save a few lines.
- Exact versions are pinned in a lockfile with hashes. Upgrades are
  deliberate, reviewed changes.
- Vendor integrations are written against the vendors' HTTP APIs directly.

## SDK vs direct API — the decision per provider

| Provider | Official SDK | Third-party SDK | Decision |
|---|---|---|---|
| Telegram | None from Telegram. | python-telegram-bot 22.8 (LGPL-3.0, tracks Bot API 10.0), aiogram 3.31.0 (MIT, Bot API 10.3) — both maintained | **Direct.** We need about eight send/edit/delete methods. These libraries are frameworks for *receiving* updates; they bring their own HTTP stack and hide the retry and error behaviour this service must own. LGPL is an avoidable licence consideration. |
| Instagram | `facebook-business` v26.0.2 (2026-09) — current | — | **Direct.** Autogenerated and ads-centric, oriented to `graph.facebook.com`; no container polling, no Instagram-Login token refresh, no resumable upload. Five endpoints are needed. |
| LinkedIn | `linkedin-api-python-client` — beta, last release 2023 | — | **Direct.** Stale, and the API requires a monthly version header we must control. |

Common reasons: all three APIs are plain HTTPS with JSON or multipart
bodies; retry classification, rate-limit handling and secret redaction have
to be ours in any case; SDK release lag would gate our ability to follow API
version changes.

### Things to keep an eye on

- **FastAPI is still 0.x** and flags breaking changes in minors. Pin exactly.
- **httpx2 is a young package name** (repository created 2026-05). It is a
  fork of httpx 0.28.1 maintained by the Pydantic organisation and adopted
  by Starlette, with 18 releases in five months. The fallback is `httpx`
  0.28.1 — an import swap — at the cost of an apparently unmaintained
  dependency.
- **Mocking libraries have not followed** httpx2 (respx and pytest-httpx
  both have open issues). We use the built-in `MockTransport`, which removes
  a dependency rather than adding one.

## Deliberately not added

| Not added | Reason |
|---|---|
| Vendor SDKs | See the table at the top. |
| SQLAlchemy / Alembic | A handful of tables and hand-written SQL. Migrations are numbered `.sql` files tracked with `PRAGMA user_version`. Revisit on a move to PostgreSQL. |
| Celery, RQ, arq, Dramatiq, Temporal; Redis, RabbitMQ, NATS | Each needs a broker or server and splits "accept the request" across two stores. A job table and a loop are enough at this volume. |
| tenacity or any retry library | Retries here are persisted state transitions (`attempts`, `run_after`) that must survive a restart and be visible on the publication, not in-memory decorators. |
| pydantic-settings, python-dotenv | A dozen settings are validated by a plain Pydantic model. |
| python-multipart | Media uploads use a raw request body, not a multipart form, so no inbound multipart parser is needed. Eight advisories since 2024-10. |
| OpenTelemetry SDK / exporters | No collector in a single-host deployment. `traceparent` is accepted and logged. |
| gunicorn / multiple workers | The design requires exactly one process (one SQLite writer, one worker loop). |
| respx, pytest-httpx | Tied to legacy `httpx`. |

## Base image

`python:3.14-slim`, pinned by digest, for build and runtime stages; a Docker
Hardened Image for Python is preferred for the runtime stage if one is
available for 3.14 at build time (free tier, Apache-2.0, requires
`docker login dhi.io`). To be settled in the Docker phase, when the daemon is
available to measure both.

## S3 signing: hand-written, no SDK

The object-storage stager makes two kinds of request (PUT, DELETE) and builds
one presigned GET URL. Options compared in
[research/testing-and-onboarding.md](research/testing-and-onboarding.md), section C:

| Option | Verdict |
|---|---|
| **Hand-written AWS Signature V4 over httpx2** (`staging/sigv4.py`, about 100 lines, standard library `hmac`/`hashlib`) | **Chosen.** Checked in `tests/unit/test_staging.py` against the three worked examples in the Amazon S3 API reference (GET object, PUT object, presigned URL): all three signatures match. |
| boto3 / botocore | Rejected. Tens of megabytes and its own HTTP stack for two requests. |
| aiobotocore, minio client | Rejected for the same reason; each brings its own HTTP client. |
| Small signer libraries | None found that works with httpx2 and is maintained. |
